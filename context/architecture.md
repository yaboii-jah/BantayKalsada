# Architecture Context

## Stack

| Layer      | Technology                            | Role                                                                                                                                          |
| ---------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework  | Next.js 14+ (App Router) + TypeScript | Full-stack framework — handles page routing, server components, SSR, and API route handlers                                                   |
| UI         | Tailwind CSS + Shadcn/ui              | Utility-first styling and accessible, unstyled component primitives (forms, modals, toasts, tables)                                           |
| Auth       | Supabase Auth                         | Email/password authentication, email verification, and password reset — all handled natively; no custom token flows required                  |
| Database   | Supabase (PostgreSQL)                 | Hosted PostgreSQL database — accessed via `@supabase/supabase-js`; schema managed via Supabase CLI migrations; RLS policies enforce access control at the database level |
| Storage    | Cloudinary                            | Cloud storage and CDN for report photos — direct browser-to-Cloudinary upload via signed preset; EXIF stripping enforced at preset level      |
| Maps       | Leaflet.js + React Leaflet            | Client-side interactive map for location pinning on report submission and display on report detail pages                                      |
| Email      | Brevo + template strings             | Transactional email delivery for report status notifications only (approved, rejected, resolved) — auth emails (verification, password reset) are sent by Supabase Auth |
| SMS        | PhilSMS REST API via `lib/sms.ts`    | Transactional SMS for citizen opt-in on report approve/reject/resolve; 3-attempt retry with 1s delay, failures logged but non-blocking |
| Push       | Web Push API + `web-push` library    | Browser push notifications via VAPID keys, service worker, and `push_subscriptions` table; Supabase Realtime for live unread badge |
| Validation | Zod                                   | Runtime schema validation on all API route handler inputs and report submission form fields                                                   |

## System Boundaries

- `app/(public)/` — Guest-accessible pages requiring no authentication: landing page (`/`), public report feed (`/browse`), and individual report detail pages (`/reports/[id]`). Report detail pages render a `DuplicateBanner` when the report's `duplicate_of_id` is set, linking to the canonical report. Logged-in non-owners can flag a report as **"Already fixed"** or **"Wrong location"** via the `FlagReportButtons` component on the detail page — flags are private (never rendered publicly) and alert admins via in-app notification. The browse feed supports keyword search via ILIKE on title + description, category filtering, status filtering, barangay filtering, map view (all filtered results as Leaflet markers with viewport-aware bounding box filtering; map defaults to Taytay center), and pagination — all driven by URL search params. The map's bounding box filter is purely client-side: the server fetches all matching reports, and the client constrains markers and count to the current viewport as the user pans/zooms. The map view overlays a severity-weighted hazard-density **heatmap under the existing clustered markers**, toggled by a single **Heat** on/off control (default on). The heatmap (when enabled) renders overall hazard density from **all** `APPROVED`/`RESOLVED` Taytay reports — an unfiltered, RLS-enforced server query selecting only `latitude`, `longitude`, `severity` — weighted per report by severity (`MINOR=1`, `URGENT=2`, `EMERGENCY=3`), via a `HeatLayer` client component (`components/maps/heat-layer.tsx`) built on `leaflet.heat` (loaded via `window.L = L` + dynamic `import("leaflet.heat")` because the plugin attaches to the global `L`). A separate **Traffic** road-color overlay (Phase B) is served via a tile proxy `GET /api/traffic/tiles/{z}/{x}/{y}` (TomTom Raster Flow Tiles, key server-only). A **base map layer toggle** (first in the toggle row) lets users switch between **Street** (OSM), **Terrain** (OpenTopoMap), and **Satellite** (ESRI World Imagery) tile sources — driven by local React state with `key={baseMap}` for clean `TileLayer` remounting. No database or cache table required. All pages in this group are Next.js Server Components and render only `APPROVED` or `RESOLVED` reports. The report detail page uses `generateMetadata` to return dynamic Open Graph (`og:title`, `og:description`, `og:image`, `og:url`) and Twitter Card (`summary_large_image`) meta tags for rich link previews when shared on social platforms. The report detail page also renders a `CommentSection` client component below the location map — any logged-in user can view and post comments; visitors without an account see a "Sign in to leave a comment" prompt. The Supabase server client used here is initialized with the anon key and relies on RLS to enforce the status filter at the database level.

- `app/(auth)/` — Unauthenticated-only pages: registration (`/register`), login (`/login`), and password reset (`/reset-password`). Email verification is handled by a Supabase-generated link — no custom `/verify-email` route is needed. All Unauthenticated users are redirected away from these routes.

- `app/(citizen)/` — Protected pages requiring an authenticated Supabase session with a verified email: report submission form (`/submit`), personal report history (`/my-reports`), individual own-report detail (`/my-reports/[id]`), own-report edit page (`/my-reports/[id]/edit`), feedback submission (`/feedback`), and personal feedback history (`/my-feedback`, `/my-feedback/[id]`). The own-report detail page renders a `DuplicateBanner` (when `duplicate_of_id` is set) and a `ReportTimeline` showing the report's lifecycle from `report_activity_log`. The submission form includes a required barangay dropdown (Dolores, San Isidro, San Juan, Santa Ana, Muzon) manually selected by the citizen via an `InlineSelect` dropdown — Nominatim reverse geocode on pin drop populates only the `location_label`, not the barangay. The map defaults to Taytay center (14.5587, 121.1360) at zoom 14. The `submitReport` Server Action validates the pinned location against the Taytay boundary via the `is_within_boundary` RPC before insert — locations outside Taytay are rejected. Citizens can also edit their own **PENDING** reports via `updateReport` — the same boundary re-validation applies only when coordinates change. Offline submission is a client-only concern: when `navigator.onLine` is false (or the `submitReport` Server Action rejects with a network `TypeError`), the form persists a draft to an IndexedDB store (`lib/offline-queue.ts`), storing photo `File` blobs plus any already-uploaded Cloudinary URLs. An `OfflineQueueProcessor` mounted in `(citizen)/layout.tsx` drains the queue on mount/`online`/`visibilitychange`, uploading pending photos and replaying `submitReport` (all server guards still run). Drafts are user-scoped; failed attempts keep the draft with `lastError` and are surfaced in an `OfflineReportsPanel` on `/my-reports`. No new server surface, schema, or dependency. The notification bell in the nav provides in-app notification access (lazy-fetched dropdown, mark-as-read, delete). Unverified users attempting to access `/submit` are redirected to a prompt to verify their email. Session is read server-side via the Supabase server client.

- `app/admin/` — Strictly protected pages requiring an authenticated session with `role: ADMIN` on the user's profile record: dashboard (`/admin`) with status count cards and analytics charts (submissions over time, category distribution, status distribution, approval rate, avg resolution time), pending queue (`/admin/pending`), status-separated report lists (`/admin/approved`, `/admin/rejected`, `/admin/resolved`) — each of the four queues is newest-first and supports title-search/category/barangay filtering driven by URL search params (`q`/`category`/`barangay`), the report review page (`/admin/reports/[id]`), the report edit page (`/admin/reports/[id]/edit`), the flags queue (`/admin/flags`) listing reports with active citizen flags, and the feedback inbox (`/admin/feedback`, `/admin/feedback/[id]`). The report review page shows a "Citizen Flags" card (flag type, flagger name, date) when citizens have flagged the report, a lifecycle `ReportTimeline` (from `report_activity_log`), and a `DuplicateManager` for linking/merging duplicates; the sidebar shows a count badge of distinctly flagged reports. The review page links to the admin edit page, where `AdminReportEditForm` edits a report's editable fields and logs an `EDITED` audit event plus an in-app `REPORT_EDITED` notification to the submitter. The feedback review page includes the `FeedbackNoteEditor` component for adding, editing, and removing admin notes. The dashboard is dynamic (`export const dynamic = "force-dynamic"`); analytics data is computed server-side via aggregate RPCs (`count_reports_by_status()`, `daily_submissions_since()`, `count_reports_by_category()`, `count_reports_by_barangay()`, `avg_resolution_hours()`, `count_reports_since()` — migration `20260820000001`, with a full-table in-JS aggregation fallback until applied) and passed to a lazily-loaded recharts client component (`analytics-charts-lazy`, `next/dynamic` `ssr:false`). The admin panel uses a **distinct dark palette**: a client `AdminTheme` mounted in the layout adds the `admin-theme` class to `document.body`, re-declaring the neutral tokens in `globals.css` as a deep blue-tinted near-black (the blue primary and semantic status colors are shared with the citizen side unchanged); because custom properties cascade, portalled Dialogs, `InlineSelect` dropdowns, Sonner toasts, and Tooltips match too, and the class is removed on navigation away. Non-admin access is blocked at the `app/admin/layout.tsx` boundary (session + `profiles.role === 'ADMIN'` check, redirecting non-admins to `/browse`) and re-verified in every admin Server Action via `verifyAdmin()` using the service-role client. The `proxy.ts` edge guard requires only authentication for `/admin` (it never reads the profile record); role enforcement lives in the layout and every action.

- `public/` — Static assets served at `/`. Contains `manifest.json` (PWA manifest), app icons (192x192, 512x512, Apple 180x180), and `sw.js` (generated service worker). The service worker is compiled from `app/sw.ts` via `@serwist/next` at build time and precaches all JS/CSS/fonts. Runtime caching uses network-first for navigations and stale-while-revalidate for images.

- `app/sw.ts` — Service worker entry point. Defines precaching for static assets, runtime caching strategies for pages and images. Also handles `push` events (receives push payload, extracts title/body/url, calls `showNotification()`) and `notificationclick` events (closes notification, navigates to the contained URL). Bundled into `public/sw.js` by `@serwist/next` during `next build`.

- `app/api/` — API route handlers. Owns no UI. Responsible for Cloudinary signed upload preset generation (`/api/uploads/sign`) — requires authentication and enforces 30 requests per hour per user rate limit via the `upload_sign_log` table. SMS diagnostics (`/api/sms/diagnose`) — admin-only endpoint that probes PhilSMS `/v3/me` and `/v3/balance` on both `app.philsms.com` and `dashboard.philsms.com` to verify token validity and credit balance. CSV export (`/api/admin/export`) — admin-only endpoint that returns a downloadable CSV of reports filtered by optional `?status=` param, using the service role client and profile join. Public REST API (`/api/reports`, `/api/reports/[id]`) — anonymous, read-only JSON endpoints exposing APPROVED/RESOLVED reports to third-party consumers. Each handler: Zod-validates query params → enforces a DB-backed sliding-window rate limit (120 req/hour + 1,000/day per SHA-256 IP hash) → delegates to the service layer in `lib/api-reports.ts` → returns the curated `{ success, data }` envelope. Reads use the anon-key server client (RLS-scoped); rate-limit bookkeeping uses the service-role client against `api_request_log`. Responses carry `Cache-Control: public, s-maxage=60, stale-while-revalidate=300` and `Access-Control-Allow-Origin: *`. Mutations (report submission, admin approve/reject/resolve) are implemented as Server Actions (`app/actions.ts`, `app/admin/actions.ts`), not API routes. Every handler validates its input with Zod before touching the database. The TomTom tile proxy (`/api/traffic/tiles/{z}/{x}/{y}`) bounds-validates tile coordinates server-side (z ∈ 0–20, x/y within `0..2^z−1`, 400 on invalid) so arbitrary coordinates cannot be proxied as abuse.

- `app/auth/callback/route.ts` — OAuth callback route. Receives the authorization code from Supabase after Google OAuth consent, exchanges it for a session via `exchangeCodeForSession()`, and redirects the user to the app. The post-OAuth `next` redirect parameter is validated by `safeNextPath()` — only relative same-origin paths are allowed (`//`-prefixed and backslash-containing values fall back to `/browse`), preventing open-redirect abuse.

- `components/` — Shared UI components not tied to a single route. Subdivided into `components/ui/` (Shadcn/ui primitives), `components/maps/` (Leaflet map components — always client-side only), `components/browse/` (filter bar, pagination, photo gallery, browse map), `components/reports/` (report card, report form, photo upload widget, status badge, share button, feedback form, feedback card, comment-section, comment-form, comment-list, comment-item, report-timeline, duplicate-banner), `components/admin/` (admin-shell, sidebar, queue table, bulk-action-bar, report-filter-bar, rejection modal, action buttons, status count cards, analytics-charts, analytics-charts-lazy, admin-list-pending, admin-list-skeleton, feedback actions, feedback-note-editor, admin-report-edit-form, duplicate-manager, admin-theme), `components/notification-bell.tsx` (in-app notification dropdown with Supabase Realtime live unread count updates), `components/push-subscription-manager.tsx` (PushSubscriptionManager, requestPushSubscription, unsubscribeFromPush), and `components/install-prompt.tsx` (PWA install banner).

- `lib/` — Shared utilities and Supabase client factories. Contains: `lib/supabase/server.ts` (Supabase server client factory — creates a per-request client using `@supabase/ssr`'s `createServerClient`), `lib/supabase/client.ts` (Supabase browser client — created once using `createBrowserClient`), `lib/supabase/middleware.ts` (session refresh helper called in `proxy.ts`), `lib/email.ts` (Brevo client), `lib/cloudinary.ts` (Cloudinary config and signing helper), `lib/validations/` (all Zod schemas including `updateFeedbackNoteSchema`), `lib/report-activity.ts` (audit helper `logReportActivity` — inserts into `report_activity_log` via the service-role client), `lib/notifications.ts` (in-app notification creation helper — supports `FEEDBACK_NOTE_ADDED` and `REPORT_EDITED` alongside existing notification types), `lib/admin-notifications.tsx` (report submitter lookup + email dispatch; also contains `sendFeedbackNotifications` for feedback notifications with optional `adminNote` parameter), `lib/sms.ts` (PhilSMS SMS client with `sendSMS()`, `normalizePhoneNumber()`, and 3-attempt retry; endpoint URL built from `PHILSMS_API_BASE` env var, defaults to `https://app.philsms.com`), `lib/push.ts` (Web Push server — `sendPushNotification()` with VAPID config via `web-push`, expired subscription cleanup), `lib/api-rate-limit.ts` (SHA-256 IP hashing + sliding-window rate limiting — `clientIp()` reads the **last** `x-forwarded-for` hop, the one appended by the trusted proxy, to resist spoofed header prefixes), `lib/api-reports.ts` (public REST API service layer — exports `sanitizeSearchTerm` for stripping filter-reserved characters from user input), and `lib/utils.ts` (general helpers).

- `supabase/` — Supabase project configuration: `supabase/migrations/` (SQL migration files generated by the Supabase CLI), `supabase/seed.sql` (seed script for the initial admin profile), and `supabase/config.toml` (local dev configuration). All schema changes are made by creating new migration files via `supabase migration new` — existing migration files are never edited.

- `emails/` — Template string HTML generators for report status and feedback notification emails. `emails/render.ts` exports seven functions: `baseLayout()`, `renderApprovedEmail()`, `renderRejectedEmail()`, `renderResolvedEmail()`, `renderFeedbackAcknowledgedEmail()`, `renderFeedbackNoteAddedEmail()`, `renderFeedbackClosedEmail()`. Auth email templates (verification, password reset) are managed inside the Supabase dashboard — they do not live in this folder. React Email was not used — `react-dom/server` cannot be imported in Next.js App Router, so emails are built via string interpolation.

## Storage Model

- **Supabase PostgreSQL**: All structured application data. The `auth.users` table is Supabase-managed and stores credentials, email verification status, and session tokens — this table is never written to directly from application code. A `profiles` table, owned by the application, is kept in sync with `auth.users` via a PostgreSQL trigger that fires on new user creation; it stores the user's display name and `role` (`CITIZEN` or `ADMIN`). The `reports` table stores title, description, category, severity, barangay, status, rejection reason, an array of Cloudinary photo URLs, latitude, longitude, a PostGIS `geography(Point, 4326)` generated column (`location`) for spatial queries, location label, and all relevant timestamps. The `municipality_boundaries` table stores the Taytay boundary polygon as a `geography(Polygon, 4326)` with a GIST spatial index, used by the `check_report_location_boundary` trigger and the `is_within_boundary` RPC for geographic enforcement. The `report_comments` table stores user comments on approved/resolved reports with single-level threading (top-level comments and flat replies). The `notifications` table stores in-app notification records (type, read status, linked report ID or feedback ID). The `feedback` table stores app feedback submissions (type, title, description, optional rating, status, admin note — a nullable text field that admins can write and update independent of the status lifecycle). The `upload_sign_log` table stores signature request timestamps for rate limiting the Cloudinary upload endpoint. The `test_sms_log` table stores one row per successful "Send Test SMS" for rate limiting the `sendTestSms` Server Action (5 per user per 24h) — RLS is enabled with no policies, reachable only through the service-role client. The `api_request_log` table stores SHA-256 hashes of client IPs (plus pepper) and timestamps for rate limiting the public REST API — RLS is enabled with no policies, so the table is only reachable through the service-role client in `lib/api-rate-limit.ts` (never via PostgREST). The `push_subscriptions` table stores browser push subscription endpoints (user_id, subscription JSON, created_at) for delivering web push notifications. The `report_flags` table stores citizen flags on approved/resolved reports (report_id, user_id, flag_type from the `report_flag_type` enum, created_at) with a `UNIQUE (report_id, user_id, flag_type)` constraint so each citizen has at most one flag per type per report. The `report_activity_log` table stores the audit trail (report_id, actor_id, action from the `report_activity_action` enum, detail jsonb, created_at) — RLS enabled with no policies, service-role only, consistent with `api_request_log`. `reports.duplicate_of_id` (nullable self-FK, `ON DELETE SET NULL`) marks a report as a duplicate of a canonical report; merged/duplicate reports are retired by this pointer, never hard-deleted. No binary file data, passwords, or auth tokens are stored in application-owned tables.

- **Cloudinary**: All report photo files (JPEG, PNG, WebP, or HEIC; up to 10 MB each; 1–3 photos per report). Photos are uploaded directly from the browser using a short-lived signed upload preset generated by `/api/uploads/sign`. The database stores only the resulting Cloudinary URL and public ID for each photo — never the binary content. EXIF metadata is stripped at the upload preset level; location is never inferred from photo metadata. Offline, the client skips photo type/size validation so any captured image is retained locally as a blob and uploaded on reconnect.

## Auth and Access Model

- **Authentication**: Users authenticate via Supabase Auth (email + password or Google OAuth). Supabase manages the full auth lifecycle natively: registration, email verification link delivery, session issuance, token refresh, password reset link delivery, and OAuth token exchange. Sessions are stored as access and refresh token pairs in `httpOnly` cookies, managed automatically by `@supabase/ssr`. Application code never handles passwords or auth tokens directly. The OAuth callback is handled by `app/auth/callback/route.ts`, which exchanges the authorization code for a session via `exchangeCodeForSession()`.

- **Email verification**: After registration, Supabase Auth sends a verification email automatically using the template configured in the Supabase dashboard. No custom token storage or Resend integration is needed for this flow. A user whose email is unverified can log in but is blocked from accessing `/submit` and from calling `POST /api/reports`. This check reads the `email_confirmed_at` field from the Supabase session server-side — it is never enforced client-side alone.

- **Roles**: Every user has a corresponding row in the `profiles` table (created automatically by a database trigger on `auth.users` INSERT) with a `role` field defaulting to `CITIZEN`. To assign the `ADMIN` role, update the `profiles` row directly via Supabase Studio or via the seed script at `supabase/seed.sql`. There is no in-app UI for role management in MVP. Route handlers read the role from the `profiles` table using the authenticated user's ID from the Supabase session.

- **Ownership**: Every report record carries a `submitted_by_id` foreign key referencing `auth.users.id`. When a citizen queries their own reports, the RLS policy on the `reports` table automatically restricts results to rows where `submitted_by_id = auth.uid()`. Route handlers never accept a user ID from the request body to determine ownership — they always read the authenticated user's ID from the server-side Supabase session.

- **Access control**: Three access tiers are enforced by a combination of RLS policies (database level) and server-side session checks (application level). (1) Public — no session required; RLS allows `SELECT` only on reports where `status IN ('APPROVED', 'RESOLVED')`; all other tables are inaccessible. (2) Citizen — valid Supabase session + verified email required; RLS allows citizens to `SELECT`, `INSERT`, and `UPDATE` their own pending reports, `SELECT`, `INSERT`, `UPDATE`, and `DELETE` their own report flags (each `flag_type` is an independent row per citizen per report — INSERT a flag, DELETE to unflag it; both types may be active at once), and `SELECT`, `UPDATE` (mark as read), and `DELETE` their own notifications. Notification `DELETE` uses the anon-key server client governed by a dedicated DELETE RLS policy. (3) Admin — valid session + `role: ADMIN` on the profile record required; admin operations use the Supabase service role client to bypass RLS. The service role key is never exposed to the browser.

## Invariants

1. **A report is never returned to the public without an explicit status filter.** The RLS policy on the `reports` table enforces `status IN ('APPROVED', 'RESOLVED')` for all public (unauthenticated) reads at the database level. Application-level filtering after fetching all records is not acceptable and must not be used as a substitute.

2. **Photo files never pass through Next.js API routes.** The browser uploads photos directly to Cloudinary using a signed preset. The `/api/uploads/sign` route issues only the signature; it never receives or proxies the file bytes. Only the resulting Cloudinary URL is sent to the server and stored in the database.

3. **The Supabase server client is created per request, never as a module-level singleton.** `lib/supabase/server.ts` exports a factory function that calls `createServerClient` on each invocation — it must be called inside each Server Component, Route Handler, or Server Action that needs database access, not at the top of a module. The browser client in `lib/supabase/client.ts` is the only Supabase client that may be instantiated once at the module level.

4. **Leaflet and React Leaflet components are never rendered server-side.** Every component that imports from `leaflet` or `react-leaflet` must be loaded using `next/dynamic` with `{ ssr: false }`. Violating this causes a `window is not defined` crash at build or runtime.

5. **Admin authorization is verified server-side in every admin Server Action.** Middleware redirects are a UX convenience only. Every Server Action in `app/admin/actions.ts` independently reads the Supabase session, fetches the user's profile via the `verifyAdmin()` helper, and confirms `profile.role === 'ADMIN'` before executing any logic. A missing session or non-admin role returns an error immediately.

6. **Rate limiting is enforced server-side.** The `submitReport` Server Action rejects submissions when the authenticated user has already submitted 5 or more reports within the past 24 hours, counted via a database query. Client-side disabling of the submit button is a UX courtesy only and cannot be relied upon.

7. **Rejection reasons are private to the report submitter.** The RLS policy on the `reports` table ensures the `rejection_reason` column is never exposed in public queries. It is returned only when a citizen reads their own report and only because the RLS policy confirms `submitted_by_id = auth.uid()`.

8. **Report status transitions are unidirectional and explicit.** The only valid transitions are `PENDING → APPROVED`, `PENDING → REJECTED`, and `APPROVED → RESOLVED`. No Server Action may accept an arbitrary status value from the client. Each transition is a dedicated Server Action (`approveReport`, `rejectReport`, `resolveReport` in `app/admin/actions.ts`) that hard-codes the target status — status is never a free-form client-supplied value.

9. **Feedback status transitions are explicit.** The valid transitions are `OPEN → ACKNOWLEDGED` and `OPEN/ACKNOWLEDGED → CLOSED`. Each transition is a dedicated Server Action (`acknowledgeFeedback`, `closeFeedback` in `app/admin/actions.ts`) that hard-codes the target status — status is never a free-form client-supplied value.

10. **Feedback rate limiting is enforced server-side.** The `submitFeedback` Server Action rejects submissions when the authenticated user has already submitted 3 or more feedback entries within the past 24 hours, counted via a database query. Client-side disabling of the submit button is a UX courtesy only and cannot be relied upon.

11. **Feedback notifications follow the same fire-and-forget pattern as report notifications.** Email and in-app notification dispatch happens after the status update succeeds, wrapped in `.catch()` so failures are logged but never block the status transition.

12. **Admin notes on feedback are updated independently of status.** The `updateFeedbackNote` Server Action modifies only the `admin_note` column and never changes feedback status. Notifications are sent only on first-time note add (null → string), not on edits or clears.

13. **Service worker caching uses specific strategies per resource type.** Static assets (JS, CSS, fonts) are precached at install time. Navigations use network-first with cache fallback (stale page loads offline). Cloudinary images use stale-while-revalidate. API routes, Supabase auth requests, and map tiles are network-only. The service worker is bundled at build time by `@serwist/next` from `app/sw.ts` and served at `/sw.js`. No runtime-generated caching rules are added client-side.

14. **Comments are soft-deleted by admin, never hard-deleted from the database.** The `removeComment` admin Server Action sets `report_comments.status = 'REMOVED'` — it never issues a SQL DELETE. The `report_comments` DELETE RLS policy only allows the original author to hard-delete their own comment. This ensures auditability and prevents data loss from malicious or accidental deletion.

15. **Comment submission rate is limited server-side.** The `addComment` Server Action rejects submissions when the authenticated user has already submitted 30 or more comments within the past 24 hours, counted via a database query. The INSERT RLS policy on `report_comments` also verifies the parent report is `APPROVED` or `RESOLVED` — comments cannot be placed on pending or rejected reports.

16. **Cloudinary upload signing requires authentication and is rate-limited.** The `/api/uploads/sign` route handler calls `supabase.auth.getUser()` and returns 401 for unauthenticated requests. Each successful request is logged to `upload_sign_log`. The handler enforces a maximum of 30 signature requests per hour per user using a sliding window count on that table.

17. **Nearby reports on the submission form are queried via PostGIS with SECURITY INVOKER and respect RLS.** The `get_nearby_reports` RPC function uses `ST_DWithin` on a GIST-indexed geography column and is gated by SECURITY INVOKER, meaning the caller's RLS policies apply. The function's WHERE clause redundantly filters `status IN ('APPROVED', 'RESOLVED')` for defense in depth. The query triggers on pin drop only, limited to 25 results, sorted by distance ascending.

18. **Every report location is enforced within Taytay boundary at two levels.** (a) A `BEFORE INSERT OR UPDATE OF latitude, longitude` database trigger (`trg_reports_location_boundary`) uses `ST_Within` against the `municipality_boundaries` table to reject any operation whose location falls outside the Taytay polygon. (b) The `submitReport` Server Action independently calls the `is_within_boundary` RPC before insert, returning a user-facing error for out-of-bounds locations. Both layers must agree — the trigger is defense in depth against code bypass, the application check provides a friendly error message to the citizen.

    > **Trigger implementation note:** The trigger constructs the point geometry inline via `ST_SetSRID(ST_MakePoint(NEW.longitude, NEW.latitude), 4326)::geometry` rather than referencing the generated `location` column (`NEW.location::geometry`). On PostgreSQL 17, geography generated columns are **not** computed before `BEFORE INSERT` triggers fire — `NEW.location` is NULL inside the trigger context. This matches the approach used by the `is_within_boundary` RPC.

19. **Push subscriptions are scoped per user and managed via Server Actions.** The `push_subscriptions` table stores one or more subscriptions per user (multiple devices). The `savePushSubscription` Server Action is the only server-side write path — RLS ensures users can only manage their own subscriptions. Expired subscriptions (HTTP 410/404 from push service) are automatically cleaned up by `sendPushNotification()`.

20. **Push notifications are fire-and-forget, non-blocking, and never prevent status transitions.** Push dispatch happens after email and SMS dispatch in notification helpers, wrapped in try-catch. A failed push (invalid subscription, expired key, unreachable push service) is logged and silently ignored — the status transition and email/SMS notifications proceed unaffected.

21. **The serwist service worker is disabled in dev mode by design** (`next.config.ts`: `disable: process.env.NODE_ENV !== "production"`). Push subscription requires the production build (`npm run build && npm start`) because `navigator.serviceWorker.ready` hangs when no SW is registered. A 15-second timeout in `requestPushSubscription` provides a clear error message in dev mode.

22. **Every report lifecycle event has an audit row.** `logReportActivity` (via the service-role client into `report_activity_log`) is called inside the Server Action immediately after the write succeeds — a status transition, edit, comment removal, duplicate link, or merge cannot occur without its audit row. The activity log is append-only and has no RLS policies (service-role only), so the timeline is a trustworthy trail. Bulk admin actions write one row per affected report.

23. **Duplicate reports are never hard-deleted.** Linking sets `duplicate_of_id`; merging first reassigns the duplicate's comments and flags to the canonical report, deduplicates photos capped at 3, then retires the duplicate via `duplicate_of_id`. Hard deletion would orphan notification and activity-log foreign keys, so it is avoided by design.

24. **Admin edits re-validate the boundary only when the pin changes.** `editReport` calls `is_within_boundary` only when `latitude`/`longitude` differ from the stored values; the `trg_reports_location_boundary` database trigger still guards every location write regardless.

25. **`REPORT_EDITED` and `REPORT_FLAGGED_OWNER` notifications are in-app only.** An admin edit notifies the submitter via the `notifications` table but never dispatches email or SMS — the edit action (`editReport`) is a separate path from the status-transition notification pipeline. Likewise, when a citizen flags a report, the report's owner receives an in-app-only `REPORT_FLAGGED_OWNER` notification (admins get `REPORT_FLAGGED`, also in-app only), and neither flag notification dispatches email/SMS/push.

26. **Duplicate-candidate search never proposes already-linked reports.** `findDuplicateCandidates` excludes the report itself and any report whose `duplicate_of_id` is already set, and requires a title search of ≥ 3 characters (or nearby matches within 1500 m via `get_nearby_reports`).

27. **User-influenced redirects are relative same-origin paths only.** Any redirect target derived from request input (e.g. the `next` param in the OAuth callback) passes through `safeNextPath()` — non-relative values, `//`-prefixed URLs, and backslash-containing values are rejected and replaced with a default path. This prevents open-redirect abuse.

28. **Every interactive write action is rate-limited server-side before it runs.** Report submission (5/24h), feedback (3/24h), comments (30/24h), report flag actions (30/24h), Cloudinary upload signatures (30/hr), and test SMS sends (5/24h) are each enforced by a count query against the relevant table in the Server Action / route handler before any mutation. Client-side disabling is a UX courtesy only.

29. **Rate-limit identity is taken from the trusted edge, and proxies validate their input.** `lib/api-rate-limit.ts` `clientIp()` reads the **last** `x-forwarded-for` hop (appended by the trusted proxy) rather than the first, so a client-supplied header prefix cannot spoof a different rate-limit bucket. The TomTom tile proxy validates z/x/y coordinates (z ∈ 0–20, x/y within `0..2^z−1`) before proxying, returning 400 for invalid tiles.
